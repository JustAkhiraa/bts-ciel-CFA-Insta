Docker — le TP d'initiation

Les six parties du sujet, question par question. Les commandes sont à taper, pas à lire : ce TP ne se révise pas, il se refait. Le cours · La fiche

1Introduction — le moteur répond-il ?

1Vérifier que Docker fonctionne Facile

1.1 Lancer docker --version puis docker info. Relever le nombre de conteneurs et d'images présents.

✅ Correction
bash
docker --version
docker info

docker --version ne dit qu'une chose : la commande existe. C'est docker info qui interroge le moteur — s'il répond, tout le reste du TP est possible.

Les deux lignes à relever sont en haut de sa sortie :

sortie
Client:
 Version:    27.3.1
...
Server:
 Containers: 0
  Running: 0
  Paused: 0
  Stopped: 0
 Images: 0

Sur une installation neuve, les deux valent 0. Les relever maintenant a un intérêt : à la fin du TP, on comparera, et on verra ce que l'on a oublié de nettoyer.

⚠️ Cannot connect to the Docker daemon

Docker Desktop n'est pas lancé (macOS, Windows), ou le service est arrêté (sudo systemctl start docker, Linux), ou l'utilisateur n'est pas dans le groupe docker et la session n'a pas été rouverte. La section 2 du cours détaille les trois cas.

2Lancer deux fois hello-world Facile

1.2 Exécuter docker run hello-world, puis relancer la même commande. Qu'est-ce qui change dans le temps d'exécution et dans les messages ? Expliquer pourquoi.

✅ Correction
bash
docker run hello-world

La première fois, Docker ne trouve pas l'image localement, va la chercher sur le registre public, et le dit :

sortie
Unable to find image 'hello-world:latest' locally
latest: Pulling from library/hello-world
c1ec31eb5944: Pull complete
Digest: sha256:...
Status: Downloaded newer image for hello-world:latest

Hello from Docker!

La seconde fois, ces cinq premières lignes disparaissent et l'exécution est quasi instantanée.

sortie
Hello from Docker!
🧭 L'explication attendue

Une image ne se télécharge qu'une fois : elle est ensuite dans le cache local de la machine, et docker run la réutilise. Le temps de la première exécution est presque entièrement du téléchargement, pas du démarrage — un conteneur, lui, démarre en quelques dizaines de millisecondes.

Conséquence pratique sur un serveur : on pull l'image avant la fenêtre de déploiement, pour que la bascule soit immédiate.

💡 Deux conteneurs, pas un

Vous venez de créer deux conteneurs, tous deux terminés. docker ps -a les montre à l'état Exited (0) : un conteneur qui a fini son travail ne disparaît pas tout seul.

2Manipuler des images

3Télécharger, lister, supprimer Facile

2.1 à 2.3 et 2.5 Télécharger alpine, nginx et httpd sans les exécuter. Lister les images locales en relevant pour chacune son nom, son tag, son identifiant et sa taille. Supprimer httpd.

✅ Correction
bash
docker pull alpine
docker pull nginx
docker pull httpd

docker images

docker rmi httpd
sortie
REPOSITORY    TAG       IMAGE ID       CREATED        SIZE
nginx         latest    3b25b682ea82   2 weeks ago    192MB
httpd         latest    f32c0b1d2e4a   3 weeks ago    148MB
alpine        latest    91ef0af61f39   5 weeks ago    7.8MB

Les identifiants et les tailles exactes dépendent du jour où vous téléchargez : ce sont des images qui évoluent. L'ordre de grandeur, lui, est stable — et c'est lui qui compte : Alpine est vingt-cinq fois plus petite que nginx.

💡 pull ne lance rien

C'est tout l'intérêt de la question : séparer avoir l'image et exécuter un conteneur. Après ces trois commandes, docker ps -a est toujours vide.

4Le tag, ou pourquoi il y a deux lignes « nginx » Moyen

2.4 Télécharger nginx:1.21, relancer docker images. Combien de lignes pour nginx ? Qu'est-ce que cela apprend sur la notion de tag ?

✅ Correction
bash
docker pull nginx:1.21
docker images
sortie
REPOSITORY    TAG       IMAGE ID       CREATED        SIZE
nginx         latest    3b25b682ea82   2 weeks ago    192MB
nginx         1.21      ea335eea17ab   3 years ago    141MB
alpine        latest    91ef0af61f39   5 weeks ago    7.8MB

Deux lignes, avec deux IMAGE ID différents.

🧭 L'explication attendue

Le tag fait partie de l'identité de l'image. Un dépôt (nginx) contient plusieurs versions, chacune désignée par un tag. nginx tout court n'est pas « le dépôt » : c'est un raccourci pour nginx:latest.

Noter aussi la colonne CREATED : « 3 years ago » pour la 1.21. C'est la date de fabrication de l'image, pas celle du téléchargement.

⚠️ latest ne veut pas dire « la plus récente »

C'est le tag employé par défaut, rien de plus. En production on épingle toujours une version explicite : un déploiement qui change tout seul parce qu'un éditeur a republié latest est un incident, pas une mise à jour.

⚠️ Supprimer une version précise

docker rmi nginx ne supprime que nginx:latest. Pour l'autre : docker rmi nginx:1.21. Le tag se précise aussi à la suppression.

3Manipuler des conteneurs

5Entrer dans une Alpine, et comprendre ps -a Facile

3.1 et 3.2 Lancer un conteneur interactif Alpine avec un terminal. À l'intérieur : ls, cat /etc/os-release, puis exit. Relancer docker ps puis docker ps -a : le conteneur apparaît-il dans les deux ? Justifier.

✅ Correction
bash
docker run -it alpine sh
sortie
/ # ls
bin  dev  etc  home  lib  media  mnt  opt  proc  root  run  sbin  srv  sys  tmp  usr  var
/ # cat /etc/os-release
NAME="Alpine Linux"
ID=alpine
VERSION_ID=3.20.3
PRETTY_NAME="Alpine Linux v3.20"
/ # exit
bash
docker ps      # vide
docker ps -a   # le conteneur alpine, a l'etat Exited
🧭 La justification attendue

Il n'apparaît que dans docker ps -a. docker ps ne liste que les conteneurs en cours d'exécution ; celui-ci est arrêté.

Et il est arrêté parce qu'un conteneur vit tant que son processus principal vit. Ici, ce processus était le sh qu'on a quitté par exit : en le quittant, on a arrêté le conteneur.

Le conteneur n'a pas disparu pour autant. Il garde sa couche d'écriture et occupe de la place, jusqu'à un docker rm.

💡 -i et -t séparément

-i garde l'entrée standard ouverte, -t alloue un pseudo-terminal. Sans -t on n'a pas d'invite ; sans -i on ne peut rien taper. Les deux vont presque toujours ensemble, d'où -it.

6Un nginx en arrière-plan, et son statut sans docker ps Moyen

3.3 et 3.4 Lancer un nginx détaché, nommé mon-serveur. Puis, sans utiliser docker ps, retrouver son statut à l'aide d'une seule commande, et expliquer la démarche.

✅ Correction
bash
docker run -d --name mon-serveur nginx

La commande rend immédiatement la main et affiche l'identifiant complet du conteneur. Pour le statut, sans docker ps :

bash
docker inspect -f '{{.State.Status}}' mon-serveur
sortie
running
🧭 La démarche

docker inspect rend toute la fiche technique du conteneur en JSON — configuration, réseau, montages, état. L'option -f applique un gabarit Go qui n'en extrait qu'un champ : .State.Status.

Sans l'option, on voit l'objet entier et on peut chercher la bonne clé :

bash
docker inspect mon-serveur | grep -i status

L'intérêt de la question n'est pas la syntaxe du gabarit, c'est de découvrir qu'inspect est la source et que ps n'en est qu'un affichage condensé.

7Journaux, shell dans le conteneur, et le fichier qui survit Moyen

3.5 à 3.7 Afficher les journaux de mon-serveur. Ouvrir un terminal dans le conteneur déjà lancé, aller dans /usr/share/nginx/html et modifier index.html. Quitter, arrêter puis redémarrer le conteneur. Le fichier modifié a-t-il survécu ? Formuler une hypothèse.

✅ Correction
bash
docker logs mon-serveur

docker exec -it mon-serveur bash
bash
# a l'interieur du conteneur
cd /usr/share/nginx/html
echo "Bonjour NetSolutions" > index.html
cat index.html
exit
bash
docker stop mon-serveur
docker start mon-serveur
docker exec mon-serveur cat /usr/share/nginx/html/index.html
sortie
Bonjour NetSolutions
🧭 L'hypothèse attendue

Oui, le fichier a survécu. stop arrête le processus principal ; il ne détruit pas le conteneur. La couche d'écriture du conteneur — celle qui enregistre tout ce qui a été modifié par rapport à l'image — est toujours là, et start la retrouve.

Ce serait l'inverse après un docker rm : cette couche serait effacée, et un nouveau conteneur repartirait de la page d'accueil nginx d'origine. C'est précisément ce que démontre la partie 5.

⚠️ exec, pas run

docker run -it nginx bash créerait un deuxième conteneur, vierge, dans lequel le serveur ne tourne même pas. On y modifierait un fichier sans aucun effet sur mon-serveur. C'est l'erreur la plus coûteuse du TP, parce qu'elle ne produit aucun message.

8Supprimer, et ce que rm refuse Facile

3.8 Supprimer le conteneur. Que se passe-t-il si on essaie de supprimer un conteneur encore en cours d'exécution ? Quelle option force la suppression ?

✅ Correction
bash
docker stop mon-serveur
docker rm mon-serveur

Sur un conteneur qui tourne encore :

sortie
Error response from daemon: cannot remove container "mon-serveur":
container is running: stop the container before removing or force remove

L'option qui force est -f :

bash
docker rm -f mon-serveur     # arrete puis supprime, d'un coup
💡 Le refus est une protection, pas une contrariété

Supprimer un conteneur actif, c'est couper un service sans prévenir. Docker demande donc un geste explicite. -f envoie un SIGKILL immédiat, sans les dix secondes de grâce de stop : une base de données peut en garder une transaction incomplète.

4Exposer un service sur un port

9Publier 8080, puis 8081, puis échouer sur 8080 Moyen

4.1 à 4.4 Lancer nginx en publiant son port 80 sur le 8080 de la machine, puis vérifier dans un navigateur. Lancer un second nginx sur 8081 : les deux conteneurs peuvent-ils utiliser le port 80 en même temps, et pourquoi n'y a-t-il pas de conflit ? Enfin, tenter un troisième sur 8080 déjà pris : expliquer le message.

✅ Correction
bash
docker run -d --name web  -p 8080:80 nginx
curl http://localhost:8080

docker run -d --name web2 -p 8081:80 nginx
curl http://localhost:8081
sortie
<!DOCTYPE html>
<html>
<head>
<title>Welcome to nginx!</title>
...
🧭 Pourquoi aucun conflit sur le port 80

Chaque conteneur possède sa propre pile réseau : son port 80 n'est pas le port 80 de la machine. Les deux peuvent donc écouter sur 80 chez eux. Ce qui doit être unique, c'est le port de l'hôte — d'où 8080 et 8081.

C'est la même mécanique que le PAT : une redirection, avec une correspondance entre un port public et un service interne.

Le troisième :

bash
docker run -d -p 8080:80 --name web3 nginx
sortie
docker: Error response from daemon: driver failed programming external
connectivity on endpoint web3: Bind for 0.0.0.0:8080 failed: port is already allocated.
🧭 Lire le message

Bind for 0.0.0.0:8080 failed — Docker a demandé au système de réserver le port 8080 sur toutes les interfaces de l'hôte, et le système a refusé : web l'occupe déjà. Côté conteneur, rien n'empêchait web3 d'écouter sur 80.

Le conteneur est tout de même créé, à l'état Created : il apparaît dans docker ps -a et il faudra le supprimer.

⚠️ La page ne s'affiche pas ?

Trois causes, dans l'ordre : on a inversé -p 80:8080 · le conteneur s'est arrêté (docker ps -a le dira) · le TP est fait sur une machine distante ou en ligne, et localhost y désigne cette machine-là, pas la vôtre.

5Persister des données avec un volume

10Un volume qui survit à la destruction du conteneur Difficile

5.1 à 5.4 Créer un volume nommé donnees-web, lancer un nginx sur le port 8082 en l'associant au dossier servi, modifier index.html, puis supprimer complètement le conteneur. Relancer un conteneur de nom différent avec le même volume : la modification est-elle là ? Qu'est-ce que cela démontre ?

✅ Correction
bash
docker volume create donnees-web

docker run -d --name web-persistant -p 8082:80 \
           -v donnees-web:/usr/share/nginx/html nginx

docker exec web-persistant sh -c 'echo "Bonjour NetSolutions" > /usr/share/nginx/html/index.html'
curl http://localhost:8082
sortie
Bonjour NetSolutions
bash
docker stop web-persistant
docker rm   web-persistant          # le conteneur n'existe PLUS

docker run -d --name web-persistant-v2 -p 8082:80 \
           -v donnees-web:/usr/share/nginx/html nginx
curl http://localhost:8082
sortie
Bonjour NetSolutions
🧭 Ce que cela démontre

Un volume ne dépend d'aucun conteneur. Il est créé séparément, il est monté par un conteneur le temps que celui-ci vit, et il lui survit. Plusieurs conteneurs peuvent monter le même, successivement ou en même temps.

La relation est donc l'inverse de ce qu'on croit spontanément : ce n'est pas le conteneur qui possède ses données, c'est le volume qui prête les siennes à un conteneur.

C'est la réponse à la question 3.7 vue de l'autre côté : sans volume, la modification mourait avec le conteneur ; avec un volume, elle lui survit.

⚠️ Le volume masque le contenu de l'image

Au tout premier montage, le volume étant vide, Docker y recopie la page d'accueil nginx d'origine. Ensuite, le volume n'est plus vide et il remplace entièrement le dossier de l'image. Si un jour une mise à jour d'image n'apparaît pas, c'est souvent un volume qui la cache.

bash
docker volume ls
docker stop web-persistant-v2 && docker rm web-persistant-v2
docker volume rm donnees-web

L'ordre de la question 5.5 n'est pas négociable : docker volume rm refuse tant qu'un conteneur, même arrêté, l'utilise.

6Nettoyage, et les trois mots

11Tout nettoyer proprement Moyen

6.1 et 6.2 Lister tous les conteneurs encore présents, puis proposer et exécuter les commandes qui nettoient tout : arrêt et suppression des conteneurs restants, suppression des images inutiles.

✅ Correction
bash
docker ps -a

Deux manières, et la seconde est la bonne :

bash
# a la main, avec les identifiants
docker stop $(docker ps -q)       # arreter tout ce qui tourne
docker rm   $(docker ps -aq)      # supprimer tous les conteneurs
docker rmi  $(docker images -q)   # supprimer toutes les images
bash
# avec les commandes de menage de Docker
docker container prune -f
docker image prune -a -f
docker volume prune -f
docker system df                  # pour verifier ce qu'il reste
🧭 Pourquoi prune plutôt que la substitution

$(docker ps -q) échoue quand la liste est vide : la commande reçoit zéro argument et répond requires at least 1 argument. Les prune gèrent ce cas, demandent confirmation, et disent combien d'octets ont été récupérés.

-q ne rend que les identifiants, un par ligne : sans lui, on passerait aussi les en-têtes de colonnes à la commande suivante.

⚠️ docker system prune -a --volumes

Cette variante emporte aussi les volumes inutilisés — c'est-à-dire les données du projet sur lequel vous ne travaillez pas aujourd'hui. Sur votre machine de TP, aucun risque ; prenez tout de même l'habitude de lancer docker system df avant.

12Image, conteneur, volume — et ce qui persiste Moyen

6.3 En quelques lignes, distinguer clairement les trois notions manipulées, en précisant pour chacune si elle est persistante par défaut.

✅ Correction
NotionDéfinitionPersistant par défaut ?
Image Un modèle figé, en lecture seule, qui contient l'application et tout ce dont elle a besoin. On ne l'exécute pas : on en dérive des conteneurs. Oui — elle reste dans le cache local jusqu'à un docker rmi.
Conteneur Une exécution d'une image, avec sa propre couche d'écriture et sa propre pile réseau. C'est l'objet vivant et jetable. Non — sa couche d'écriture survit à un stop/start, mais disparaît au docker rm.
Volume Une zone de stockage gérée par Docker, extérieure aux conteneurs, qu'un conteneur monte à un emplacement donné. Oui — il survit à la suppression des conteneurs qui l'utilisent, et ne part qu'avec un docker volume rm.
🧭 La phrase qui résume les trois

« L'image est le modèle, le conteneur est l'exécution, le volume est la mémoire. Seuls le modèle et la mémoire survivent ; l'exécution est faite pour être jetée. »

C'est aussi ce qui fait la force du procédé : un conteneur qu'on peut détruire sans rien perdre est un conteneur qu'on peut remplacer à chaque mise à jour, sans sauvegarde et sans migration.
