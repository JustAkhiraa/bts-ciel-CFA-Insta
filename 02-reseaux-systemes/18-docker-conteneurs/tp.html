Docker Lab 1 · monter le laboratoire

Le montage du laboratoire du TP, pas à pas : d'abord installer Docker sur une machine Linux, puis lever les quatre machines (client, serveur, attaquant, routeur) avec le script de gestion. C'est cette maquette qui sert aux TP de réseau et de cybersécurité : dont l'attaque MITM sur SSH. Cochez les actions au fur et à mesure ; les commandes se copient d'un clic.

🎯 Avant de commencer

Le laboratoire tourne sur votre machine Linux (physique ou virtuelle) : Docker y crée un réseau 192.168.56.0/24 et quatre conteneurs. Tout reste sur l'hôte. Pour l'installation, il faut les droits d'administrateur (sudo devant chaque commande, ou une session root).

Le détail des adresses et des rôles est au chapitre 10 du cours ; les autres systèmes (Debian, Fedora, macOS, Windows) sont au chapitre 2.

01Installer Docker sur Linux

Sur Linux, on ajoute le dépôt officiel Docker aux sources du système, puis on installe le moteur. L'exemple suit Ubuntu ; Debian est quasi identique.

hôte · root
apt update
apt install ca-certificates curl gnupg
hôte · root
install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg | gpg --dearmor -o /etc/apt/keyrings/docker.gpg
chmod a+r /etc/apt/keyrings/docker.gpg
💡 Ce que fait cette série

curl télécharge la clé, --dearmor la convertit au format binaire attendu par apt, et chmod a+r la rend lisible. La clé sert ensuite à vérifier la signature des paquets Docker : on n'installe que ce qui vient bien de Docker.

hôte · root
echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \
  tee /etc/apt/sources.list.d/docker.list > /dev/null

apt update
💡 Les deux variables

$(dpkg --print-architecture) donne l'architecture du processeur (souvent amd64), et $(. /etc/os-release && echo "$VERSION_CODENAME") le nom de code de la version d'Ubuntu (jammy, noble…). Le dépôt est ainsi choisi automatiquement pour votre machine.

hôte · root
apt install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
hôte · root
systemctl status docker
sortie attendue
docker.service - Docker Application Container Engine
   Loaded: loaded (/lib/systemd/system/docker.service; enabled; preset: enabled)
   Active: active (running) since ...
hôte · root
gpasswd -a etuciel docker
⚠️ Il faut se reconnecter

L'appartenance à un groupe n'est lue qu'à l'ouverture de session : déconnectez-vous puis reconnectez-vous (ou redémarrez la session) pour que docker fonctionne sans sudo. Et rappelez-vous que le groupe docker donne, de fait, les droits root sur l'hôte.

02Lever le laboratoire

Le laboratoire est fourni comme un script de gestion, gestion_lab1.sh, qui crée le réseau, les volumes et les quatre conteneurs d'un seul geste.

hôte
bash gestion_lab1.sh -c
💡 Les options du script

-c crée (le réseau, les volumes, les conteneurs), -s stoppe, -l relance ce qui a été stoppé, -d détruit tout (conteneurs et volumes). On y revient à la partie 5.

🔌 Après un redémarrage du PC

Les conteneurs sont alors arrêtés, pas supprimés. On ne refait pas -c (qui recrée tout à neuf, travail perdu) : on relance.

hôte
bash gestion_lab1.sh -l        # relance les 4 machines d'un coup
# ou, sans le script, tous les conteneurs arretes :
docker start $(docker ps -aq)
docker ps                      # verifier : 4 en marche

docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"
for ip in 10 11 12 254; do ping -c 1 -W 1 192.168.56.$ip > /dev/null \

1Les trois adresses du client Facile

Le client est en 192.168.56.11, sa passerelle est 192.168.56.254, son DNS est 192.168.56.10. Expliquer pourquoi ces trois adresses ne désignent pas la même machine, et ce que chacune fait.

✅ Correction

Les trois adresses du client jouent trois rôles différents, et c'est tout le plan d'adressage d'un réseau :

  • 192.168.56.11 : la sienne. C'est à elle qu'on s'adresse pour le joindre.
  • 192.168.56.254 : sa passerelle, le routeur. Tout paquet destiné à une adresse qui n'est PAS dans 192.168.56.0/24 part chez lui. Sans elle, le client ne sort pas de son réseau.
  • 192.168.56.10 : son DNS, le serveur. C'est lui qui traduit srvssh.local.ciel.fr en adresse. Sans lui, les adresses numériques marchent encore et les noms ne marchent plus : le symptôme le plus courant, et le plus mal diagnostiqué, de tout le programme.
🛠️ Le test qui sépare les trois

ping 192.168.56.10 réussit et ping srvssh.local.ciel.fr échoue : le réseau va bien, c'est le DNS qui ne répond pas. Les deux échouent : c'est le réseau. Ce couple de commandes est le premier geste d'un diagnostic, et il tient en dix secondes.

04Depuis l'hôte, ou depuis ailleurs

depuis l'hôte
ssh etuciel@192.168.56.10
depuis une autre machine
# l'adresse de l'HOTE, et le port publie
ssh etuciel@192.168.1.42 -p 12222

2Pourquoi deux commandes différentes Moyen

Pourquoi ssh etuciel@192.168.56.10 ne marche-t-il pas depuis le poste du voisin ?

✅ Correction

Parce que 192.168.56.0/24 n'existe pas en dehors de l'hôte. C'est un réseau que Docker a créé sur cette machine-là ; aucun routeur de la salle n'en a entendu parler, et un paquet envoyé à 192.168.56.10 depuis le poste du voisin part chez sa propre passerelle, qui ne sait qu'en faire.

D'où les ports publiés. -p 12222:22 dit à l'hôte : « ce qui arrive sur TON port 12222, passe-le au port 22 de ce conteneur ».

Le voisin parle donc à l'hôte, qu'il sait joindre, et c'est l'hôte qui fait suivre. C'est le mécanisme des ports publiés, à l'échelle de quatre machines.

⚠️ Un port publié ouvre une porte sur le réseau

Un port publié est joignable par toute la salle, pas seulement par vous. Quatre machines avec SSH, c'est autant de portes : dont une sur un Kali Linux.

Sur un réseau partagé, on vérifie ce qu'on expose, et on arrête la maquette quand on a fini.

05Stopper, ou supprimer

hôte
ssh etuciel@192.168.56.11 "echo essai > ~/preuve.txt"

bash gestion_lab1.sh -s     # stoppe
bash gestion_lab1.sh -l     # relance
ssh etuciel@192.168.56.11 "cat ~/preuve.txt"
sortie
essai

3Stopper n'est pas supprimer Moyen

Le fichier a survécu au -s / -l. Même question après un bash gestion_lab1.sh -d suivi d'un -c. Expliquer la différence avec ce que montre docker volume ls.

✅ Correction

Après -s puis -l, le fichier est là. Il n'était pas dans le conteneur : il était dans un volume, monté sur /home/etuciel. Un conteneur stoppé, puis relancé, retrouve son volume.

hôte
docker volume ls
sortie
DRIVER    VOLUME NAME
local     home_client_lab1
local     home_kali_lab1
local     home_routeur_lab1
local     home_serveur_lab1

Après -d, cette liste est vide : le script supprime les volumes en même temps que les conteneurs. Un -c qui suit recrée tout à neuf, et preuve.txt n'existe plus nulle part (voir les volumes).

🛠️ La règle, en une phrase

Entre deux séances : -s. En fin de TP, et seulement après avoir récupéré ce qu'on veut garder : -d. Ici, se tromper coûte une séance de travail.

⚡ Le Lab 1 en cinq gestes

  • Installer : dépôt officiel, clé GPG, moteur et plugins, puis systemctl status docker.
  • Lever : gestion_lab1.sh -c crée réseau, volumes et quatre conteneurs.
  • Vérifier : docker ps et un balayage ping ; les trois adresses du client (la sienne, la passerelle, le DNS).
  • Accéder : depuis l'hôte par l'IP du conteneur, d'ailleurs par l'IP de l'hôte et un port publié.
  • Ranger : -s stoppe sans rien perdre, -d supprime volumes compris.
